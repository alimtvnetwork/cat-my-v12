# 00 - Blind-AI Spec Audit Overview

**Audit:** Plan 22 - Blind-AI Spec Audit of `spec/21-app/`
**Target:** `spec/21-app/` (61 files, inventoried in `inventory.csv`)
**Companion input:** `app/` (Python capture/audit runtime) and `.lovable/coding-guidelines.md` (if present) plus `spec/coding-guidelines/`.
**Persona under test:** a "blind AI" - a non-frontier model that receives ONLY the `spec/` folder and must implement the product without asking questions, without inferring from filenames, and without access to the `app/` source tree.

## Purpose

Determine, per spec file, whether a blind AI can implement the described behaviour with zero ambiguity. Every ambiguity, missing checklist, missing enum casing, missing database diagram, missing image explanation, missing facade/SDK contract, or missing error taxonomy MUST be logged as a numbered issue with a score and a fix instruction.

## Output shape

- `00-overview.md` (this file)
- `01-rubric.md` - scoring rubric (0-100 per spec file, weighted dimensions)
- `02-scope.md` - what is in scope, what is explicitly out of scope
- `03-inventory.md` - human-readable inventory summary (source: `inventory.csv`)
- `04-guideline-crosswalk.md` - map every spec file to the coding guideline sections it must obey
- `10-issues/NN-<spec-slug>.md` - one issue file per spec file (padded to two digits then spec basename)
- `90-summary.md` - aggregate scores, blocker list, next-plan hand-off
- `99-consolidated.md` - single-file bundle regenerated by `scripts/audit_consolidate.py`

## Conventions (non-negotiable)

1. Every enum, verdict, tier, retention policy, or state name in this audit MUST be written in PascalCase (e.g. `TierOne`, `RetentionShort`, `Pass`, `Fail`, `Error`). Any spec that uses lower/UPPER/kebab casing for these is an issue.
2. Every spec file MUST end with a checklist a blind AI can tick. Missing checklist = issue.
3. Every image referenced by a spec MUST have a prose explanation (what it depicts, what the AI must reproduce). Missing explanation = issue.
4. Every persistence surface MUST have a database diagram or table DDL block. Missing = issue.
5. Every SDK integration MUST follow the `<Vendor><Domain>SdkFacade` facade pattern with `Cat`-prefixed domain objects (see `spec/21-app/52-sdk-facade-pattern.md`). Non-conforming = issue.
6. Every error path MUST cite a code from the `E_*` taxonomy (`E_CAP_*`, `E_AUDIT_*`, `E_SPEC_*`). Bare `throw`/`raise` = issue.
7. No em dash (-) allowed in spec prose. Use commas, colons, or period-separated sentences.

## Reader guarantee

A blind AI reading `spec/21-app/` plus `spec/coding-guidelines/` MUST be able to answer, for every feature: what to build, what data shape to persist, which enum values are legal, which errors to raise, which SDK facade to call, and how to verify success. If any of those seven answers is missing, the audit records an issue against the responsible spec file.
